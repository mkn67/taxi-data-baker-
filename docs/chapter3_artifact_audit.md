## Defects found and changes made

1. Both benchmark CLIs defaulted to `local[4]` outside containers and only printed a warning when the master was not Standalone. Full-mode CLI and notebook runs now require a `spark://` master and two active worker hosts visible through the Spark REST executor endpoint. Pilot mode remains clearly tagged `local_functional` when it uses local Spark.
2. Compose mounts the host event-log folder at `/opt/spark/work-dir/logs/spark-events`; path resolution previously selected `/opt/spark/logs/spark-events` inside the container. The engine now uses the mounted path. The driver also binds to the configured container host when `SPARK_DRIVER_HOST` is set.
3. Failed metric collection previously represented unavailable counters as zero. Missing metrics now remain null. TSR and PSR scopes are recorded; TSR is max successful-task executor runtime divided by its median in the selected completed stage. PSR is max/median records for that same stage and is emitted only when every successful task has one consistent record metric. The selected stage is the completed stage with maximum total shuffle read plus write bytes, with executor runtime as tie-breaker. Zero denominators produce unavailable ratios.
4. Historical canonical CSVs were overwritten without a backup. CLI and notebook runs route outputs to separate local-functional, standalone-pilot, and official-Standalone CSVs and plan directories; replacements within a tier are backed up and written atomically. Measured iterations save executed plans and runtime/config metadata in run rows.
5. Hotspot-loading failures could silently substitute a fixed, undocumented ID set. The benchmark now fails if it cannot read the artifact or reproduce the set from Silver.
6. The join DuckDB audit calculated distinct pickup-zone counts but did not compare them. It now checks that value as well as trip counts, fare, mileage, and borough-pair coverage.
7. A reproducible Gold density builder was added at `scripts/03_build_gold_spatial_analysis.py` and run on 2026-10-30. It creates zone-by-period GeoParquet/CSV, a spatial audit, and the Chapter 3.1 density figure. This builder uses DuckDB, GeoPandas, and Matplotlib; this successful spatial run is not evidence of Spark cluster execution. Its boundary grouping uses the project’s approximate 60th Street geometry rule and excludes ambiguous zones from the south-vs-north comparison.

The spatial builder applies the existing 5% side-area rule and centroid-side agreement to every Manhattan zone. The boundary audit originally scoped its candidate review to zones within 1 km of the line; extending the rule citywide is a documented design choice for this builder, not a result already approved by a separate project protocol. The 16 candidate assignments in the existing audit match, but that does not establish that the citywide groups are the project’s final CRZ definition. Confirm the interpretation before presenting them as such. The line remains approximate and the output is descriptive.

## Benchmark design and implementation status

### ND2 aggregation

The code compares baseline `groupBy(PULocationID)`, uniform salting, and selective salting with S=8. Both salted strategies use a true two-stage aggregation. The selected bucket is derived deterministically from pickup time, drop-off time, and trip miles; selective salting splits only pickup IDs in the P95 hotspot artifact. All branches aggregate the same Silver records and produce count, average fare, and total miles. DuckDB validation compares all three measures for each pickup zone.

Remaining evidence needed: rerun full ND2 with the updated code on the two-worker Standalone cluster; retain run metadata and executor evidence; verify final task-level metrics are available from the Spark REST API; attach the exact P95 threshold/hotspot IDs and same-run input fingerprint to the official run metadata. Existing CSVs are not official candidates because they lack execution-mode provenance.

### ND3 OD join

The join key is `(PULocationID, DOLocationID)`, inner join semantics. Baseline disables AQE and broadcast; AQE enables adaptive skew join with factor 2 and a 16 MiB threshold; salted join assigns salts to trips from the pickup-hotspot set and replicates matching OD rows over salts 0–7. The join audit groups by pickup/drop-off borough and checks trip count, total miles, fare, distinct pickup zones, and pair coverage. Salting correctness depends on the OD matrix being unique per composite key; the benchmark’s independent DuckDB aggregate check detects business-result duplication or loss but should be supplemented by explicit OD-key uniqueness evidence in an official run.

Remaining evidence needed: rerun on Standalone; save final executed physical plans after materialization for each measured method; show whether Spark actually split skew partitions for AQE (configuration alone is insufficient); record exact AQE values and active executor hosts; repeat the zero-duplicate OD-key check for the same manifest; keep local functional outputs labeled separately.

## Reproducibility commands

From the repository root, after both workers are healthy and registered, first confirm the driver has the Python packages needed by the scripts:

```bash
podman exec spark-driver python3 -c 'import duckdb, pandas, numpy; print("benchmark dependencies import")'
podman exec spark-driver python3 -c 'import geopandas, shapely, pyarrow; print("spatial dependencies import")'
podman exec spark-driver /opt/spark/bin/spark-submit --version
```

The first command must succeed, and the second must report Spark 3.5.9. If the container lacks DuckDB/Pandas/NumPy or GeoPandas/Shapely/PyArrow, the image needs a reproducible dependency setup before these commands can run. Then execute from the repository root:

```bash
podman exec spark-driver env SPARK_MASTER_URL=spark://spark-master:7077 SPARK_EXPECTED_VERSION=3.5.9 \
  /opt/spark/bin/spark-submit --master spark://spark-master:7077 \
  --deploy-mode client --conf spark.driver.host=spark-driver \
  --conf spark.driver.bindAddress=0.0.0.0 \
  --conf spark.executor.cores=1 --conf spark.executor.memory=1500m --conf spark.cores.max=4 \
  /opt/spark/scripts/run_benchmark_nd2.py --mode full \
  --master spark://spark-master:7077 --partitions 200

podman exec spark-driver env SPARK_MASTER_URL=spark://spark-master:7077 SPARK_EXPECTED_VERSION=3.5.9 \
  /opt/spark/bin/spark-submit --master spark://spark-master:7077 \
  --deploy-mode client --conf spark.driver.host=spark-driver \
  --conf spark.driver.bindAddress=0.0.0.0 \
  --conf spark.executor.cores=1 --conf spark.executor.memory=1500m --conf spark.cores.max=4 \
  /opt/spark/scripts/run_benchmark_nd3.py --mode full \
  --master spark://spark-master:7077 --partitions 200
```

The engine fails full mode unless the driver reports Spark 3.5.9, sees a Standalone master, and reports active executors on at least two worker hosts. Run CSVs and plan directories are tier-suffixed so pilot/local evidence stays separate from official Standalone results. The current host requirement pin is 3.5.6, so use the matching Compose Spark distribution or align the Python environment before running. Confirm the needed Python packages (`duckdb`, `pandas`, `numpy`) are importable in the chosen driver environment; the Compose image package inventory could not be inspected here. Keep the Spark Master UI and application UI evidence, output run CSV, matching plan files, event logs, and audit CSV together for the final research record.
